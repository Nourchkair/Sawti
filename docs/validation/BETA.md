# Sawti Beta validation record

Beta extends the completed internal Alpha workflow with app-audio capture and stronger meeting-scale reliability evidence. It preserves the existing CoreAudio process-tap architecture, permission boundaries, consent flow, local ASR adapters, immutable original transcript, and recovery queue. This record deliberately distinguishes source presence and automated coverage from a pass on an actual meeting service.

## Route and behavior matrix

| Route | Existing implementation | Required Beta evidence | Status |
|---|---|---|---|
| In-person microphone | Alpha's in-bundle helper for mic-only; live app/dual-source capture uses `AudioCaptureSession` | Existing marker, 10-minute, offline, and crash-recovery evidence plus repeated/long-session checks for app's dual-source route | Alpha core pass; Beta soak and dual-source microphone-stall checks open |
| Zoom desktop | Native meeting assertion/title detection plus process-tree app tap and optional microphone track | A real Zoom call, remote speech visibly audible in Sawti's app track, local speech in mic track, non-silent verification, correct meeting start/end, timestamped transcript, and preserved originals | Not run on Sawti; Zoom.app is installed, but no live call has been captured |
| Teams desktop | Native Teams detection plus bundle process-tree tap and optional microphone track | A real Teams call, including helper-process audio, both track checks, timestamps, transcript completeness and recovery; repeat with per-app output routing | Not run; Teams.app is not installed on the host |
| Google Meet in Chromium | Browser WebRTC assertion, explicit consent, concrete browser-process identity, app-process tap | Synthetic browser fixture pass followed by a real Meet session with consent; verify remote audio, transcript, stop/end behavior, and unrelated tab audio boundary | Synthetic lane exists; Chrome is not installed on the host. Actual Meet not run |
| Google Meet in Safari | Manual app picker can target a running Safari process; generic WebRTC assertion is not proven for Safari | Manual selection and real Meet capture; separately test automatic detection before claiming it | Not run. Browser-tab isolation is not implemented; app-process capture may include audio from other tabs |

Browser meeting detection is intentionally broad: a Chromium/WebRTC signal can represent a non-meeting call, so the user must approve recording. It targets an application process, not an individual browser tab. Native Teams and Zoom detection remains subject to the actual process/assertion names seen on supported app and macOS versions. Manual app selection is the fallback when auto-detection does not match.

## Ordered Beta gates

1. **B0 — Test-harness identity and path correctness.** The canonical path helper and disposable-home LaunchServices propagation are implemented. Path tests, shell syntax, `git diff --check`, and the full shell script tests pass. The isolated app/AudioTapLib/mt-cli suites also passed in this work. Re-run the test suites on the final Beta commit before calling B0 complete. No test lane may infer success from output in Meeting Transcriber's legacy data directories.
2. **B1 — Capture pipeline regression.** The isolated app (including deterministic browser-consent state tests), AudioTapLib, mt-cli, and shell script tests passed. One earlier synthetic no-mic process-tap recording and local reimport completed with expected sidecar track selection and retained transcripts. A later delayed-onset repeat was blocked by current macOS screen-recording permission denial before fixture playback, so the repeated capture/completeness gate is not closed. The active-duration comparison is not a reliable completeness oracle; marker alignment, a successful repeat, live browser consent, and route-interaction checks remain open. Do not treat one synthetic run as a general capture pass.
3. **B2 — Real-service capture.** For Meet, Zoom, and Teams separately, record a consented 10-minute session with scripted remote/local markers. Check audio-frame coverage, track RMS/active duration, source transcript, final transcript, monotonic timestamps within the audio duration, meeting identity, stop behavior, and that the first intended spoken marker is captured. Repeat a service using a non-default per-app output device if the service offers one. The current simulator starts playback alongside the meeting assertion; a release claim about complete meeting onset needs a separate onset test (O-14).
4. **B3 — Transcript quality and speaker behavior.** Use a fixed reference transcript and at least two known speakers per service. Report WER/CER and DER/JER (or explain where reference diarization is unavailable); inspect overlap, name spelling, speaker switches, timestamp boundary error, language changes, and the preservation of raw ASR segments. A generic `S1` is acceptable when the recording contains one speaker; Sawti must not invent real names.
5. **B4 — Recovery and long-session reliability.** Exercise stop, app quit, forced interruption, cold restart, back-to-back meetings, browser tab/process exit, output changes, and at least a 60-minute soak. Require the original audio and raw transcript to remain recoverable, no cross-meeting transcript merge, bounded capture failure reporting, and a queue that reaches a terminal state or an actionable error.
6. **B5 — Offline and security behavior.** Confirm model inference works from the local cache with Wi-Fi off (user accepted this check for Alpha), protocol/remote-provider generation stays disabled in the core path, audio/transcript/sidecar files remain owner-only, no meeting content appears in IPC or logs, and no network call is required during recording or ASR. First-run model acquisition remains an explicit one-time network dependency.

## Evidence collected in this Beta work

- Source review confirms native Teams/Zoom patterns, generic Chromium WebRTC detection with consent, browser process identity handling, manual app capture, `AudioCaptureSession`, and `AppTapSession` are already implemented. Source presence is not a runtime pass.
- Upstream PR #456's system-wide ScreenCaptureKit default was reviewed and rejected upstream; its permission expansion and regressions make it unsuitable as a default Sawti fix. The scoped process tap remains the primary path.
- Upstream issue #699/#712 and open PR #713 describe app tracks that can remain silent when a meeting app renders to a different output endpoint. The upstream #772 silent-track rebuild is present but off by default. These remain explicit route-qualification risks.
- The E2E scripts were found to use the old `MeetingTranscriber` app-data/output directories after Sawti's storage namespace changed. `scripts/lib/sawti-paths.sh` now supplies the Sawti paths and explicitly passes an optional disposable `SAWTI_TEST_HOME` through LaunchServices; without that, the shell driver and GUI app could disagree about where the token lives. A signed dev-app launch with the local model cache reached authenticated `/healthz` in 22 seconds and created a 64-byte token with mode 0600. The launch-time test home must be inside macOS's temporary directory, as the app enforces. The isolated Swift app suite reported 3,475 passing test outcomes; real-model/preload cases are opt-in and skipped by the isolated harness unless explicitly enabled. `tools/audiotap` passed 449 tests; `tools/mt-cli` passed 33 tests; and the shell syntax/diff/script suite passed after the path-isolation changes.
- One synthetic process-tap record-only run completed with `noMic=true`; its sidecar correctly had an app track and no microphone track. The captured app WAV had 34 seconds of detected active audio, compared with 37.5 seconds in the fixture. This difference is a follow-up concern, not a verified speech-loss percentage: energy windows are not ground-truth. The WAV was reimported through local WhisperKit; the job reached completion and retained both an engine-original transcript and a processed transcript. The engine-original was 623 bytes with nine timestamped segments; the processed transcript was also 623 bytes with six speaker-labeled, merged segments. Both artifacts and the WAV/sidecar files had mode 0600. There was no reference transcript for this exact fixture, so this establishes pipeline completion and artifact preservation, not WER or complete phrase recognition; one trailing English token in the processed text is unverified and needs quality review.
- A later delayed-playback onset attempt correctly refused to count a run that never reached the recording state. The current startup log reported `screen-recording=denied,accessibility=denied`, then `Failed to translate any of 1 PIDs to audio objects`. The driver exited before the simulator's delayed fixture playback; no recording or transcript artifact was created. This is a macOS permission-state blocker on this launch, not evidence that capture passed or that the earlier successful run is invalid. Recheck Sawti's Screen & System Audio Recording permission state and repeat the onset gate before claiming Beta capture readiness. The harness now normalizes isolated paths consistently with the app and its unit tests pass.
- A path-isolated, two-minute no-microphone soak smoke test completed the record-only route and finalized app/mix WAVs plus a sidecar, all mode 0600. The silent synthetic mix was 266.31 seconds, with no mic track. A short run without the full recording warm-up reported an apparent 1,980 MB/hour increase because its window included the initial memory ramp; after the normal 120-second recording warm-up, the two-minute window fell from 171 MB to 57 MB and passed the harness's 500 MB/hour catastrophe bound. Neither short result is a meaningful leak benchmark or a substitute for a full soak.
- For that single cached-model run, ASR processed 46.96 seconds of audio in 118.11 seconds (~2.52× audio duration), offline diarization took 4.58 seconds, and the overall job took 132.51 seconds. These are one-run observations on a MacBook Air M2/8 GB, not release performance guarantees; repeat benchmarks, accuracy qualification, peak memory, and thermal behavior remain open. See O-12/O-13 in `docs/OPTIMIZATION_BACKLOG.md`.
- The repository contains three reference-quality audio fixtures and a checked-in WER/DER baseline. Its listed WhisperKit large-v3-turbo WER is 0.2642–0.2904; the listed Sortformer DER ranges from 0.0597 for two speakers to 0.3286 for four speakers. These inherited fixture results show an existing measurement foundation, but they were not rerun as part of this Beta work and do not establish accuracy on Sawti's recording route or Nour's classes.
- A direct cached-model offline diarization run on `two_speakers_de` passed its automated quality test and measured DER 0.5697 in 6.3 seconds on the Apple M2/8 GB host running macOS 26.6.2. The test's 0.85 threshold is intentionally permissive because the short offline fixture is known to under-cluster; this score is a measured result, not proof of reliable speaker labels. A WhisperKit WER test was started with the local large-v3-turbo cache, but remained idle without output for more than two minutes and was stopped before a score was produced. No ASR quality result is claimed from that attempt.
- A read-only envelope comparison of the one recorded app-track WAV (63.38 s) to the 49.77 s simulator source produced a best log-RMS-envelope correlation of 0.9916 over 45.95 s at an approximate 3.8 s source offset. This reveals a synchronization difference worth explaining; the E2E fixture has no ground-truth turn script, so it is not evidence by itself that speech was dropped. The product's first-spoken-marker capture remains an open gate (O-14).
- The first 60-minute synthetic soak attempt reached its measurement window but did not finalize through the harness: the shell exited with a syntax error after the script was edited while the run was active. Its memory samples do not count as a pass. The harness was corrected to wait for the token/health endpoint instead of failing during asynchronous launch, then rerun without edits during the test. On the MacBook Air M2/8 GB development host, the isolated `noMic=true` silent process-tap soak passed: seven post-warm-up samples stayed at 43 MiB (0 MiB/hour fitted growth), lifetime peak 146 MiB, and app/mix WAVs plus sidecar were finalized with mode 0600. The two WAVs were 3,736.31 seconds; sidecar wall interval was 3,741 seconds. The sidecar contained an app track and no mic track. This establishes one silent synthetic long-session capture/finalization and stable app-process footprint on this host; it does not establish speech completeness, actual service behavior, thermal stability, MacBook Pro behavior, or two-hour use.
- Current host inventory has Zoom but no Teams or Google Chrome. A live Zoom test still requires a real call. Actual Teams and Chromium Meet validation requires installing/launching those clients or using a supported existing installation; this plan does not treat a synthetic fixture as proof of a service-specific route.

## Beta completion rule

Beta is complete only when B0–B5 pass or each unmet route is explicitly marked unsupported and removed from the product claim. Missing software, a missing live meeting, a silent capture track, an unbounded recording fault, or a transcript loss is **not** a pass. Performance figures in `docs/OPTIMIZATION_BACKLOG.md` remain measured observations and provisional targets; they are not substitutes for these reliability and data-integrity gates.
