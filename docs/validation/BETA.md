# Sawti Beta validation record

Beta extends the completed internal Alpha workflow with app-audio capture and stronger meeting-scale reliability evidence. It preserves the existing CoreAudio process-tap architecture, permission boundaries, consent flow, local ASR adapters, immutable original transcript, and recovery queue. This record deliberately distinguishes source presence and automated coverage from a pass on an actual meeting service.

## Speaker-to-participant matching by service

Participant rosters identify who is present; they do not, by themselves, identify which diarized voice said each utterance. Sawti must not infer that mapping from participant-list order, speaking time, role, or mute state. Enrolled voice embeddings remain the only automatic name source until a service provides a reliable link between a participant identity and the captured audio. Roster names remain optional suggestions, and generic labels plus manual naming remain available.

| Service | Names and identity clues available | Sawti status and safe next step |
|---|---|---|
| Microsoft Teams desktop | The People panel exposes attendee names and status to screen-reader navigation. Teams also offers a Get Participant API to apps running in the Teams meeting context; that API is not a general participant feed for an unrelated macOS menu-bar app. | Sawti currently makes a best-effort Accessibility read for Teams names. Treat those as manual suggestions only. First validate the roster read and any self-participant marker against real Teams recordings; do not claim that roster data identifies remote voices. ([Teams screen-reader guide](https://support.microsoft.com/en-US/accessibility/teams/use-a-screen-reader-to-join-a-meeting-in-microsoft-teams), [Teams meeting APIs](https://learn.microsoft.com/en-us/microsoftteams/platform/apps-in-teams-meetings/meeting-apps-apis)) |
| Zoom desktop | The Participants panel displays participant names and meeting roles. Zoom documents ordering by categories such as host/co-host, raised hands, unmuted, and muted; this is not speaking-time order. The documented Zoom REST participant report is for past meetings and requires an eligible paid account. | Sawti does not currently read Zoom's roster. Inspect the actual macOS Accessibility tree with the panel open, then validate that names are participant suggestions only. Do not use panel order or mute state to name a voice. ([Zoom participant management](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0065566), [Zoom past-meeting participants API](https://developers.zoom.us/docs/api/meetings/)) |
| Google Meet in Chromium | Meet's People panel exposes participant names and roles to screen-reader navigation. The Meet REST API can return participant display names and sessions with user authorization; it does not label Sawti's diarized audio segments. | Sawti does not currently read browser rosters, and browser capture is process-scoped rather than tab-scoped. Validate the Chromium Accessibility tree and unrelated-tab boundary before exposing roster suggestions. Keep API/OAuth integration out of this local capture step. ([Meet screen-reader guide](https://support.google.com/meet/answer/15738543), [Meet participants API guide](https://developers.google.com/workspace/meet/api/guides/participants)) |

The service work proceeds Teams first (existing reader), Zoom second, and Chromium Meet third. For each, collect a consented recording with a marked speaker-to-name reference, measure false assignments as well as correct ones, and enable automatic participant naming only when a repeatable service signal ties the name to the voice. Until then, roster entries stay selectable chips and unknown voices stay generic.

## Ordered Beta gates

1. **B0 — Test-harness identity and path correctness.** The canonical path helper and disposable-home LaunchServices propagation are implemented. The current worktree passed shell syntax, `git diff --check`, all shell script tests, and the isolated app/AudioTapLib/mt-cli suites. Repository-wide lint still has unrelated baseline violations. No test lane may infer success from output in Meeting Transcriber's legacy data directories.
2. **B1 — Capture pipeline regression.** The isolated suites pass, and the main-actor Whisper startup fix is covered by deterministic tests. The current stable-signed build passed the synthetic no-microphone process-tap E2E: it reached RPC, reported permissions healthy, entered recording before speech, saved a sidecar and non-silent app track, and created no microphone track. The earlier `AudioDeviceCreateIOProcIDWithBlock` stall is covered by a regression test that verifies the UI remains responsive and the attempt times out. Marker alignment, live browser consent, and route-interaction checks remain open under B2/B4; one simulator run is not service qualification.
3. **B2 — Real-service capture.** For Meet, Zoom, and Teams separately, record a consented 10-minute session with scripted remote/local markers. Check audio-frame coverage, track RMS/active duration, source transcript, final transcript, monotonic timestamps within the audio duration, meeting identity, stop behavior, and that the first intended spoken marker is captured. Repeat a service using a non-default per-app output device if the service offers one. The simulator now passes its delayed-onset lane; complete service meeting-onset evidence (O-14) remains open.
4. **B3 — Transcript quality and speaker behavior.** Use a fixed reference transcript and at least two known speakers per service. Report WER/CER and DER/JER (or explain where reference diarization is unavailable); inspect overlap, name spelling, speaker switches, timestamp boundary error, language changes, and the preservation of raw ASR segments. A generic `S1` is acceptable when the recording contains one speaker; Sawti must not invent real names.
5. **B4 — Recovery and long-session reliability.** Exercise stop, app quit, forced interruption, cold restart, back-to-back meetings, browser tab/process exit, output changes, and at least a 60-minute soak. Require the original audio and raw transcript to remain recoverable, no cross-meeting transcript merge, bounded capture failure reporting, and a queue that reaches a terminal state or an actionable error.
6. **B5 — Offline and security behavior.** Confirm model inference works from the local cache with Wi-Fi off (user accepted this check for Alpha), protocol/remote-provider generation stays disabled in the core path, audio/transcript/sidecar files remain owner-only, no meeting content appears in IPC or logs, and no network call is required during recording or ASR. First-run model acquisition remains an explicit one-time network dependency.

- Upstream issue #699/#712 and open PR #713 describe app tracks that can remain silent when a meeting app renders to a different output endpoint. The upstream #772 silent-track rebuild is present but off by default. These remain explicit route-qualification risks.
- The E2E scripts were found to use the old `MeetingTranscriber` app-data/output directories after Sawti's storage namespace changed. `scripts/lib/sawti-paths.sh` now supplies the Sawti paths and explicitly passes an optional disposable `SAWTI_TEST_HOME` through LaunchServices; without that, the shell driver and GUI app could disagree about where the token lives. A signed dev-app launch with the local model cache reached authenticated `/healthz` in 22 seconds and created a 64-byte token with mode 0600. The launch-time test home must be inside macOS's temporary directory, as the app enforces. The isolated Swift app suite reported 3,475 passing test outcomes; real-model/preload cases are opt-in and skipped by the isolated harness unless explicitly enabled. `tools/audiotap` passed 449 tests; `tools/mt-cli` passed 33 tests; and the shell syntax/diff/script suite passed after the path-isolation changes.
- One synthetic process-tap record-only run completed with `noMic=true`; its sidecar correctly had an app track and no microphone track. The captured app WAV had 34 seconds of detected active audio, compared with 37.5 seconds in the fixture. This difference is a follow-up concern, not a verified speech-loss percentage: energy windows are not ground-truth. The WAV was reimported through local WhisperKit; the job reached completion and retained both an engine-original transcript and a processed transcript. The engine-original was 623 bytes with nine timestamped segments; the processed transcript was also 623 bytes with six speaker-labeled, merged segments. Both artifacts and the WAV/sidecar files had mode 0600. There was no reference transcript for this exact fixture, so this establishes pipeline completion and artifact preservation, not WER or complete phrase recognition; one trailing English token in the processed text is unverified and needs quality review.

The harness now normalizes isolated paths consistently with the app and its unit tests pass.

## Beta completion rule

Beta is complete only when B0–B5 pass or each unmet route is explicitly marked unsupported and removed from the product claim. Missing software, a missing live meeting, a silent capture track, an unbounded recording fault, or a transcript loss is **not** a pass. Performance figures in `docs/OPTIMIZATION_BACKLOG.md` remain measured observations and provisional targets; they are not substitutes for these reliability and data-integrity gates.
